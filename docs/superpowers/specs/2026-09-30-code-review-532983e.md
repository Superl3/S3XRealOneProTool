# 커밋 532983e 코드 검토 (2026-09-30)

대상: `532983e Add in-app video enhancer, glasses IMU, and gesture robustness work` (95 파일, +7,624/−615). 코드 읽기와 단위 테스트 실행으로만 확인했고 기기 실행은 하지 않았다. 영역 4개(enhance / imu / tracking / recording·capture)를 병렬 검토한 뒤 상위 발견을 코드에서 다시 대조했다. **[직접 대조]** 표시는 검토 작성자가 코드로 확인한 것, 표시 없는 항목은 병렬 검토 보고를 옮긴 것이다.

## 결론

1. `VideoEnhancer.verify`는 프레임을 한 장도 디코드하지 않는다. 트랙 존재·크기·길이 ±1 s·샘플 수 ≥ 99 %만 본다. 기기 테스트에서 보라색 캐스트가 난 출력이 이 검증을 통과해 원본 3개가 지워졌다(`2026-09-29-enhancer-imu-dataset.md` 165·193행). 삭제 게이트를 고치기 전까지 `rec_enhance_delete_original` 기본값 켬은 위험하다.
2. 검출기 입력을 `isoPoints`로 바꾼 것은 방향이 맞지만, 기기에서 튠된 핀치 0.28/0.38·엄지 0.85/1.0 상수를 재튠하지 않았고 "실기기 미검증" 목록에도 없다.
3. 단위 테스트 `./gradlew testDebugUnitTest --offline`: 종료 코드 0, 49 클래스 282개, 실패 0, 건너뜀 3. 스펙 204행과 일치.

권장 순서: H1 → H2 실기기 확인 → M4·M5·M6(작은 수정 3개) → 나머지.

## High

### H1. 검증이 구조만 보고 원본을 지운다 [직접 대조]

`VideoEnhancer.kt:541-569` `verify()`는 비디오 트랙 존재, 가로세로, 길이 ±1 s, `samples < samplesWritten * 0.99`만 검사한다. 픽셀은 보지 않는다.

- 셰이더가 검은 화면·색 오류를 내도 통과한다. 보라색 캐스트(스펙 193행)가 실제로 통과해 원본 3개가 지워진 사례가 이미 있다.
- 디코드 실패 프레임은 조용히 빠지고 `samplesWritten`은 빠진 뒤의 수라서, 40 %가 빠져도 통과한다. `n - rendered`(`:327`)는 보고만 되고 삭제 게이트가 아니다. `:298`은 `rendered == 0`만 막는다.
- `:313 out.finish()` → `RecordingOutput.kt:81-91`은 `IS_PENDING=0` update 실패를 로그만 남기고 반환한다. 반환값이 없어 `:323`이 이어서 원본을 지운다. 결과 MP4는 pending으로 남고, 다음 앱 시작의 `recoverPending()`(`RecordingOutput.kt:357-360`)이 `_enhanced` pending 항목을 무조건 삭제한다. 원본·결과가 모두 사라지는 경로다. 확률은 낮지만 복구 불가.
- 테스트 없음. `VideoEnhancer`·`EnhanceService`는 JVM 테스트가 없다.

권고: `finish()`가 성공 여부를 반환하게 하고, 삭제 조건을 `finish 성공 && (n - rendered) == 0 && samples == samplesWritten`으로 묶는다. 픽셀 검사가 없는 동안은 기본값을 "원본 유지"로 두는 편이 맞다. 정상 MP4는 stbl 샘플이 전부 읽혀야 하므로 0.99 여유는 근거가 없다.

### H2. `isoPoints` 전환으로 임계값이 조용히 재보정됐다 [직접 대조]

`HandTracker.kt:77`이 y를 `height/width`(0.5625)배한 `isoPoints`를 만들고, `CursorPipeline.kt:295`가 모든 검출기 입력을 `result.points`에서 이것으로 바꿨다. 2026-09-28 검토가 지적한 1.78배 이방성을 없애는 올바른 방향이다.

문제는 `PinchDetector.kt:41,49`의 0.28/0.38, `FistDetector.kt:64-65`의 엄지 veto 0.85/1.0이 옛 좌표계에서 기기 튠된 값(주석 2026-07-22/23)이라는 점이다. 손목→검지 MCP가 세로인 자세에서는 분모가 1.78배 줄어 같은 물리 간격의 ratio가 커지고 핀치가 더 꽉 쥐어야 인식된다. 가로 자세에서는 반대다. 커서 세로 이득도 0.75→0.5625(`RelativeCursorMapper` 상수 제거)로 25 % 달라졌다. 스펙 "실기기 미검증"(207-218행)에 이 항목이 없다. 기존 테스트는 전부 가로 합성 랜드마크라 잡을 수 없다. 설정 슬라이더 범위(`HandSettings.kt:77`, 0.20–0.36)로 옛 감도를 복원하지 못할 수 있다.

## Medium

### M1. 주먹 ring 1프레임 깜빡임이 핀치 누름을 버린다 [직접 대조]

`CursorPipeline.kt:392` `fistPending = !isFist && enterProgress > 0f`는 curl EMA가 한 프레임만 0.95 아래로 내려가도 true다. `:393` `fistAbandoned = fistWasPending && !fistPending && !isFist`. `:425` `pressed && (fistAbandoned || (fistPending && rawPinchEvent == UP))`이면 상태기계·핀치를 리셋한다. 핀치 홀드 중 나머지 손가락을 굽힌 자세(검지 curl≈1.0, 엄지가 검지 끝에 닿아 thumbExtension<0.85)에서 한 프레임 pending → 다음 프레임 해제 = abandoned → 누름 폐기. 3프레임 뒤 DOWN이 다시 잡혀 hold 타이머가 0부터 시작하므로 드래그 진입이 늦어지거나 클릭으로 바뀐다. 엄지를 떼는 방식으로 핀치를 풀면 UP 순간에도 pending이라 클릭이 사라진다. 로그 한 줄만 남는다. 테스트 없음.

### M2. 느슨한 주먹이면 터치 드래그가 멈춘다 [직접 대조]

`CursorPipeline.kt:673`은 `curl < ENTER_THRESHOLD(0.95)`일 때만 slop·위치를 갱신한다. `isFist`는 `FistDetector.kt:48` `EXIT_THRESHOLD 1.20`까지 유지된다. curl EMA가 0.95–1.20에 머무는 주먹이면 터치는 눌린 채 위치가 고정되고 커서(`filteredDragPosition`)도 멈춘다. "펴는 중 고정" 의도가 "덜 꽉 쥠"과 구분되지 않는다. curl 상승 델타로 판정해야 한다. 테스트 없음.

### M3. not-ready 게이트가 진행을 지우고 하단 손을 지속 차단한다

`CursorPipeline.kt:382` `allowEnter = ready && fistMayStart` → `FistDetector.kt:103-115` else 분기가 `debounce.reset()`, `enterProgress = 0`. 21개 랜드마크 중 하나가 0.02(세로 11 px) 안으로 한 프레임 튀면 225 ms 진행이 0으로 돌아가고 NOT_READY 힌트가 800 ms 뜬다. `HandReadiness.kt:24`가 손목까지 검사해서 팔을 내린 자세(손목 y>0.98)에서는 핀치·주먹이 계속 막힌다. 커서는 움직이므로 사용자는 "클릭이 안 된다"만 느낀다. `EyeCaptureService.kt:1827`의 하단 존 무시와 겹치는 영역인데 조율이 없다. `HandReadinessTest`는 단일 프레임 분류만 본다.

### M4. 크래시 후 갤러리 `.gcsv`가 pending 고아가 된다 [직접 대조]

`RecordingOutput.kt:334-372` `recoverPending()`은 `MediaStore.Video`만 훑는다. 사이드카는 `MediaStore.Files`에 `IS_PENDING=1`로 만들어진다(`:150-152`). 녹화 중 앱이 죽으면 MKV는 복구되지만 `.gcsv`는 pending으로 남고, `findSidecarUri`(`:189-195`)의 기본 query가 pending을 제외하므로 `openSidecar`(후처리 입력)·`deleteSidecar`(원본 삭제 시 동반 삭제) 모두 그 파일을 못 본다. MediaStore가 약 7일 뒤 지운다. 결과: 그 MKV는 "IMU 없음"으로 후처리되고, 삭제해도 시간당 110 MB짜리 파일이 남는다.

### M5. 깜빡임 방지 −1이 되돌리기를 안 한다 [직접 대조]

`UvcCameraHelper.kt:714` `want.powerLineFrequency >= 0`일 때만 SET_CUR을 보낸다. 50 Hz로 바꾼 뒤 "카메라 기본(−1)"으로 돌리면 아무것도 보내지 않아 카메라는 50 Hz에 머문다. 같은 함수의 노출 경로(`:721-735`)는 GET_DEF(0x87)로 되돌리는데 깜빡임 방지에는 그 경로가 없다. UVC PU 컨트롤은 재오픈 뒤에도 유지된다(코드 주석 `:719-720`). 수정은 노출과 같은 방식.

### M6. Android 14의 `onTimeout(int)`이 오버라이드되지 않았다 [직접 대조]

`EnhanceService.kt:150`은 `onTimeout(startId: Int, fgsType: Int)`만 있다. SDK jar 확인 결과 android-34에는 `onTimeout(int)`만, android-35에 `onTimeout(int, int)`가 추가됐다. minSdk 34 기기에서 dataSync 6시간 예산이 끝나면 콜백을 못 받아 시스템이 서비스를 강제 종료한다. S25 Edge(Android 17)에서는 재현되지 않는다. 1-인자를 추가하고 2-인자가 그것을 부르게 하면 끝난다.

### M7. 자이로를 안 썼어도 `.gcsv`를 지운다

`RecordingOutput.kt:266` `delete()`는 MKV 삭제 성공 시 항상 사이드카를 지운다. `GcsvReader.read`가 null/예외(`VideoEnhancer.kt:194-199`)이거나 피팅 실패·R²<0.7이면 결과 MP4는 영상 기반으로 보정됐고, 이 gcsv는 이제 어떤 파일에도 매칭되지 않는다(Gyroflow는 이름으로 매칭). 스펙 47행이 의도한 동작이지만 `stabilization != "gyro"`일 때는 남기는 편이 맞다.

### M8. 정상 `stop()`이 가짜 실패를 앱 로그에 찍는다 [직접 대조]

`XrealImuClient.kt:70-77` `stop()`은 다른 스레드에서 `socket.close()`를 부른다. `read()`에 블록된 IMU 스레드는 `SocketException("Socket closed")`를 던지고, `:91-98` catch가 `thread !== me` 검사(`:101`) 전에 `onFailure(msg)`를 호출한다. 녹화 중지·USB 분리마다 메인 화면에 "Glasses IMU: Socket closed"가 뜬다. catch 안에서 `if (thread !== me) break`를 `onFailure` 앞에 두면 된다.

### M9. "169.254 네트워크 없음"은 앱 로그에 안 나간다 [직접 대조]

`XrealImuClient.kt:84-86`은 `Log.d`만 찍는다. 안경 개발자 메뉴에서 이더넷을 끈 경우, 네트워크가 늦게 올라오는 경우에 VPN 사건과 똑같이 "4분 녹화, 자이로 로그 0개, 화면 표시 없음"이 된다. `EyeRecorder.kt:437`의 "Gyro log dropped"도 logcat 전용이다. 스펙 132행의 수정이 이 경로는 덮지 않는다.

### M10. 한 `read()`의 샘플이 같은 로컬 시각으로 붕괴한다 [직접 대조]

`XrealImuClient.kt:134` 한 `read()`의 샘플은 모두 같은 `now`를 받는다. `ImuClock.kt:28`에서 `cur == null`(연결 직후)이거나 `delta - cur > 1 s`(TCP 정지 후 몰아서 도착)이면 버스트 안의 매 샘플이 새 최소가 되어 `deviceTimeNs + delta == now`, 즉 전부 같은 시각이 된다. `GyroHistory.add`(비증가 거부)는 첫 샘플만 남기고, `GyroLog`는 같은 t로 중복 기록 → `GcsvReader`가 `t <= last`로 버림 → 버스트 길이만큼 `.gcsv`에 구멍. 연결 직후는 한 read(≈30 ms)라 작지만 1 s 넘는 정지 뒤에는 밀린 샘플 전체가 사라진다. `clockKeepsTheSmallestDelayAndFollowsAJump`는 샘플마다 다른 수신 시각을 넣어 이 경우를 안 탄다. 수정: read당 마지막 샘플만 추정기에 넣고 나머지는 `local_last − (t_last − t_i)`로 채운다.

### M11. 바이어스 학습 게이트가 원시 rate를 본다 [직접 대조]

`HeadMotionCompensator.kt:71-72` `rate = |∫g|/dt`는 바이어스를 빼기 전 값(`:76`에서 뺀다)이다. 실제 바이어스가 0.03 rad/s(1.7 °/s) 이상이면 영원히 "정지"로 판정되지 않아 학습이 안 되고, 커서가 `k·bias`(0.9×0.03 ≈ 0.027 widths/s, 960 px 기준 약 26 px/s)로 계속 흐른다. `gyroBiasIsLearnedWhileTheHeadIsStill`은 bias 0.01로 게이트 아래라 통과한다. 게이트를 `|g/dt − bias|`로 바꿔야 한다.

## Low

- **L1** `GyroHistory.kt:40-57` `integrate`에 최대 간격 검사가 없다. `GyroSeries.integrate`(20 ms 초과 → null)와 달리 구멍 위로 직전 rate를 hold해 적분한다. M10의 재연결 뒤 커서가 한 번 튄다.
- **L2** `VideoEnhancer.kt:209-212` 보정값 교체 규칙이 R² 비교다. R²는 녹화마다 머리 움직임 양에 따라 달라 기준이 아니고, 설정 화면에 지우기·재보정 항목이 없다. 안경·거치가 바뀌면 옛 고R² 값이 영구히 남는다. 두 세그먼트의 지연 차이(75/45 ms)는 코드로 확정 못 함. 후보: 재연결 직후 TCP 큐잉 지연이 최소지연 추정기에 보이지 않아 오프셋이 편향. `ImuClock` 오프셋과 녹화별 적합 지연을 로그로 남기면 다음 세션에서 판별 가능.
- **L3** `VideoEnhancer.kt:74-79` `frameIntervalUs`는 간격 분포가 이봉이면 무너진다(1 ms/66 ms 교대 → 중앙값 1 ms → 66 ms 전부 제외 → 4배속). 이 카메라는 32–36 ms에 몰려 실제로는 안 걸린다. `FrameTimingTest`는 단봉만 다룬다.
- **L4** `FrameAssembler.kt:112`, `UvcCameraHelper.kt:515-518` 수정의 실효성이 협상된 `dwMaxPayloadTransferSize`에 달려 있는데 그 값이 두 스펙 문서 어디에도 없다. Eye가 실제 프레임(p95 172 KB)보다 작은 값을 보고하면 원래 버그가 돌아온다. `EyeMjpegReplayTest`는 `maxPayloadSize=0`만 돈다. 수정 빌드 녹화 173906이 7,319프레임 오류 0이라 이 기기에서는 문제없어 보인다. 값을 문서에 적고 그 값으로 재생 테스트 하나를 두면 닫힌다. 나머지 FrameAssembler 로직(full read = 계속, ZLP 처리, 타임아웃)은 맞다.
